# M2 and M2b: Q binary random access and device families

The Q profile now supports mixed random word/dword read (0403/0000), mixed
random write (1402/0000), and random bit write (1402/0001). Batch and random
tests are generated over the expanded device/command tables. Runtime remains
stdlib only; client tests use the pinned pymcprotocol 0.3.0 distribution.
Other profile capabilities, ASCII, 4E, and iQ-R remain later milestone work.

## Wire layout and mutation

Layouts were read directly from `.venv/Lib/site-packages/pymcprotocol/type3e.py`:
`randomread`, `randomwrite`, and `randomwrite_bitunits` (lines 593–727).
Each Q binary device descriptor is a three-byte little-endian head and a
one-byte device code. Random word/dword counts are separate uint8 fields.

| Operation | Payload following command/subcommand | Response data |
|---|---|---|
| Random read | word count, dword count, word descriptors, dword descriptors | uint16 words, then uint32 dwords, all LE; no counts |
| Mixed random write | word count, dword count, word descriptor + uint16 value entries, then dword descriptor + uint32 value entries | Empty |
| Random bit write | count, descriptor + one-byte 0/1 entries | Empty |

Client values are signed; storage is unsigned. A dword occupies two word
locations, with its low word at the lower address. The handler validates the
complete length, every device/range/access and every bit value before writing.
The existing server lock covers the whole request, including reads. Writes
then apply in wire order (word section first), so later duplicate or overlapping
entries overwrite earlier ones. There is no new public memory API.

The client rejects 256 before sending because a count field is only one byte.
A valid raw count of 256 does not exist. Tests instead send 256 entries with
wrapped or widened count fields and require an error with no mutation. The
batch `max_points` option does not alter random commands' uint8 count fields.
The 255-word plus 255-dword response is below the client's 4096-byte recv limit.

## Q device table

Codes, bases and kinds match the installed client's `mcprotocolconst.py`.
Every row has an inclusive default range **0..0xFFFFFF**, a synthetic ceiling
from the three-byte address format. These are not authoritative PLC capacities.
`Memory(limits={name: (min, max)})` overrides ranges per family in device points;
word views of bit devices validate the entire 16/32-point span.

names explicitly. Each timer contact, coil and current-value family has its
own sparse storage. Writes do not execute timers/counters or update peers.

## Validation and remaining assumptions

The baseline was 118 green tests. Tests were added first; the initial full RED
run had 137 failures and 183 passes, from unsupported random dispatch, absent
families, and absent base/range metadata. After strengthening the new golden
write/range tests and adding read-tail validation cases, targeted RED checks
still failed. The first implementation run passed all **323 tests**. No M1
test files (`test_m1_*.py`) or fixtures were changed. The M0 table invariant
`test_codes_and_bases_match_pinned_client` had one proven assumption bug: it
used a constant's name as the client parser spelling. It now uses the explicit
SS/SC/SN mapping for parser calls; constant lookup still uses canonical names.

Manual-derived byte vectors and exact error-code assertions remain marked
`unverified`. New design choices awaiting PLC/manual verification:

- Both-zero random read returns empty lists; empty random writes are no-ops.
- Dword access on bit devices uses two packed words (32 points), with the
  existing 16-point head alignment policy.
- Malformed random lengths use C061; invalid devices/access/bit values use
  C05C; range overflow uses C056. Existing error provenance remains
  `source=design`, `status=unverified`.

The per-device range metadata is complete for this synthetic Q profile;
authoritative vendor capacities remain open. No execution model, gates,
evidence scripts, or other archived infrastructure was introduced.
